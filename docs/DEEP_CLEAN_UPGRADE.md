## 0. Что изменилось с последнего прохода (сводка)

С момента согласования этапов 1+2 проект продвинулся дальше плана:

**Реализовано (было в плане):**
- Этапы 1–2 полностью: слои A–C, честный учёт (`planned`/`removed`/`freed` по томам,
  `recycled`, `confidence`), пересечения, защищённые пути, возрастные фильтры,
  `MAX_ACTIONS`, экран «Глубокая очистка» с планом до удаления.
- Очистка выполняется по подтверждённому плану (`CleanEngine.clean_plan`),
  без пересборки.
- Слой D (остатки/пользовательские данные) всегда отправляется в корзину.
- Корзина по всем томам через `SHQueryRecycleBinW`/`SHEmptyRecycleBinW`.

**Добавлено сверх плана:**
- Точка восстановления Windows перед глубокой очисткой (чекбокс в настройках).
- Белый список путей («никогда не удалять») — учитывается в `Planner` через конфиг.
- Экспорт плана в JSON/CSV из окна плана.
- Тип операции в истории (smart/deep/clean) + фильтр.
- Доп. цели: Epic Games, Adobe Media Cache, Java Deployment Cache, WSL vhdx
  (обнаружение + подсказка), Docker (`system prune`).
- Еженедельная тихая очистка по расписанию + CLI `--smart-clean --silent`.
- Службы и задания планировщика — на вкладке автозагрузки.
- Git-репозиторий, CI с тестами/ruff/mypy/сборкой.

**Текущее покрытие:** 49 целей (A: 36, B: 4, C: 9, D: свои правила).
238+ тестов зелёные. Незаконченная работа: график «освобождено по месяцам»
в истории (не закоммичен — не трогаем).

**Чего всё ещё нет (гэпы относительно исходного плана):**
- Системный слой B, дающий самые большие гигабайты: `DISM /StartComponentCleanup`,
  `Windows.old` и остатки обновлений Windows, файл гибернации (`hiberfil.sys`),
  очистка старых точек восстановления (VSS). Именно разница между «потенциалом
  ~18 ГБ» из аудита и текущим «безопасным набором ~7 ГБ».
- Слой E «Крупные файлы» (только показ) — не реализован.
- D1 «orphan-AppData» (остатки удалённых программ) — не реализован.
- Классификация ошибок удаления (`locked` / `access_denied` / `in_use`…):
  сейчас вплывает сырой текст, в UI «Ошибки: N» без разбор причин.
- Предупреждение «приложение запущено — его кэш очистится частично».
- Auto-discovered кэши не показываются на экране глубокой очистки
  (только внутри Smart Clean).
- Deep-очистка не участвует в расписании и не запускается по порогу места.

## 1. Цель апгрейда

1. **Больше освобождаем.** Замкнуть разрыв 7 ГБ → 14–18 ГБ: системный слой
   (DISM, гибернация, VSS) — последние «большие легальные» объёмы.
2. **Лучше понимаем результат.** «Ошибки: 2» → «2 файла заняты, закрыть
   X и повторить» — результат становится действием, а не приговором.
3. **Работаем сами.** Порог свободного места + расписание = глубокая очистка
   происходит без ручного визита.
4. **Ничем не жертвуем безопасностью.** По умолчанию ничего не выбрано,
   план до удаления, необратимое — только с отдельным явным подтверждением.

**Не делаем (осознанно):** реестровые «чистильщики», сжатие NTFS, TRIM,
`chkdsk`, изменение размера pagefile, удаление `C:\Windows\Installer`,
`C:\ProgramData\Package Cache`. Это либо не очистка, либо необратимая порча
обновлений приложений; вынесено в слой E «только показ», где при необходимости
и появится.

## 2. Этап 5A — системный слой: гигабайты (B-цели)

Оценка выигрыша по замерам аудита и типичной машине: **+5–9 ГБ**.

### 5A-1. WinSxS: `DISM /Online /Cleanup-Image /StartComponentCleanup` 🟡

**Что.** Новая командная B-цель `dism_cleanup`. Только для админа; без
`/ResetBase` (он необратим и ломает удаление обновлений — его не делаем вовсе).
Таймаут 15 мин, отмена между фазами невозможна → кнопка «Стоп» честно
говорит «DISM не прерывается», а не имитирует отмену.

**Почему.** WinSxS после пары лет обновлений содержит 4–8 ГБ «заменённых»
компонентов; это официальный, поддерживаемый Microsoft путь (`DISM`) вернуть
2–5 ГБ. Чистильщики его либо не делают, либо делают `/ResetBase` — мы делаем
безопасный вариант.

**Честность результата.** Логический размер WinSxS на диске почти не меняется
(жёсткие ссылки), поэтому `freed` для этой цели считаем **только по дельте
свободного места тома** (`volume_delta`); если дельту измерить не удалось
(цель упала по таймауту) — `freed = 0` и статус `ERR` с текстом DISM.
Никогда не показываем «освобождено N ГБ» из логического размера.

**Риск/митигация.** DISM падает/зависит от службы Trim (`trustedinstaller`):
ловим коды выхода, в UI — причина DISM (`0x800f0906` и т.п. → «службе
не хватает места/файлов»), служба никем не глушится. Точка восстановления
(уже есть) создаётся до операции.

### 5A-2. Гибернация: показ + обратимое отключение 🟢

**Что.** B-цель `hibernation`: 1) показ размера `hiberfil.sys` (обычно
40% RAM — на 32 ГБ это ~12,9 ГБ); 2) действие «отключить»: `powercfg -h off`,
frees немедленно виден в дельте тома; 3) `restore_hint` с обратной командой
`powercfg -h on` — всегда печатается в плане и отчёте.

**Почему.** Самая большая одна-файловая цель на ноутбуках, а «обратимость»
достигается одной командой. Отдельное состояние, а не кэш: поэтому не входит
ни в «Безопасный набор», ни в расписание — только явный выбор пользователя.

**Риск/митигация.**
- Потеря гибернации и быстрого запуска: текст цели честно говорит это в
  `loss`/`restore_hint`.
- Если `hibernation` не разрешена ОС/групповой политикой — цель `SKIP`,
  а не ошибка.
- Ничего не удаляем внутри `C:\`: `powercfg` сам управляет файлом.

### 5A-3. VSS: удаление старых точек восстановления 🟡

**Что.** Показ списка точек (дата) и действие «оставить самую новую,
удалить остальные»: `vssadmin list shadows` + повторный
`vssadmin delete shadows /for=<vol> /oldest` (кроме последней).
Колько храниться? Категорически нельзя трогать самую новую точку — её
создаёт наша же опция «точка восстановления перед очисткой».

**Почему.** `ShadowStorage` растёт незаметно (предел часто 10% диска, на 512 ГБ
это до 50 ГБ в худший случай); Windows обрезает его сам, но только по лимиту
квоты. Пользователи с «странным исчезающим местом» объясняются этим чаще
всего.

**Риск/митигация.** Необратимо для удалённых точек → 1) действие доступно
только с правами админа; 2) в подтверждении отдельный текст «старые точки
восстановления будут удалены»; 3) всегда оставляем самую новую; 4) `freed`
— только по дельте тома (VSS не даёт логического размера).

### 5A-4. Остатки обновления Windows: Windows.old и «соседи» — только показ 🟢

**Что.** E-показ (без удаления): `C:\Windows.old`, `$WINDOWS.~BT`,
`$WinREAgent`, `ESD\Download` — размер, дата, объяснение «вернуть откат
до 10 дней», кнопка-подсказка «удалить штатным «Временные файлы» Windows».

**Почему.** Поддерживаемый способ удалять Windows.old — внутренние механизмы
Windows (Storage Sense/cleanmgr). Ручной `rmdir` требует захвата владельца
и ломает репарации — это анти-паттерн. Показ + честная подсказка даёт
пользователю путь без риска, при этом число (например, 24 ГБ) мотивирует
пойти в настройки Windows.

**Риск/митигация.** Читаем размеры только с админом; без прав — «🔒 показать
не удалось» вместо половинного числа.

## 3. Этап 5B — честная диагностика результата

### 5B-1. Классификация ошибок удаления 🟡

**Что.** `PlannedAction`/`CleanResult` получают поле `error_kind`:
`not_found` / `locked` / `access_denied` / `in_use` / `readonly` /
`path_too_long` / `cloud_placeholder` / `unknown` — по `errno`/`winerror`
(разбор в одном месте, `services/error_kinds.py`).
В результате цели из `errors: [path…]` группа агрегируется:
«не удалось: 12 — из них занято 9, отказ 3». В диалоге результата — топ-3
пути с причиной; свежая причина = действие: «закройте X и повторите».

**Почему.** Сейчас одна строка «Ошибки: 2» без причины — главный минус UX
vs. «продукты уровня CCleaner/BleachBit». Классификация — это то, что делает
диагностику полезной, и тривиально mechanically (один mапа кодов).

**Тесты.** таблица `errno → kind`, агрегация «9 из 12».

### 5B-2. «Приложение запущено — кэш очистится частично» 🟢

**Что.** Перед построением плана проверяем запущенные процессы из фиксированного
словаря (`chrome.exe/edge.exe/firefox.exe/discord.exe/telegram.exe/steam.exe/…`,
через `tasklist /NH /FO CSV` один вызов). Совпадение с целями плана —
предупреждение в плане до удаления и в подтверждении: «Chrome запущен —
занятые файлы будут пропущены, остальное очистится».

**Почему.** Самая частая причина «освободилось 0 после очистки» —
занятые файлы браузера. Дёшево (один `tasklist`) и снимает главный
"почему не сработало".

### 5B-3. Метрики плана: время и «лучший кандидат» 🟢

**Что.** В окно плана добавляем «План построен за 4.2 с, 61 232 файла».
План строяится с `perf_counter`; при `truncated` — другое объяснение:
«показано 200 000 из 700 000».

**Почему.** DoD исходного плана: «планирование A-слоя до 90 с», а проверки
долга не было — теперь есть видимая метрика, и мы поймём деградацию
рано.

### 5B-4. Действия в результате: корзина и повтор 🟢

**Что.** Строка результата получает кнопки: «📭 Открыть корзину»
(`explorer shell:RecycleBinFolder`) и «↻ Повторить очистку» (перепланирование
только заблокированных целей).

**Почему.** После «в корзину: 4 ГБ» естественно завершить действие —
открыть корзину, откуда можно одной командой получить реальные гигабайты.

## 4. Этап 5C — автоматизация и охват

### 5C-1. Порог свободного места → предложение глубокой очистки 🟢

**Что.** Настройка `deep_threshold_gb` (по умолчанию 10, 0 = выключено).
Дашборд измеряет свободное место (уже есть `get_disk_free`); ниже порога:
баннер «C: осталось 4.2 ГБ — запустить глубокую очистку?» → переход
на экран глубокой очистки с выбранным «Безопасным набором» (пользователь
всё равно подтверждает план).

**Почему.** Большинство пользователей идут clean, когда «диск кончился;
по паспорту продукта это основной сценарий. Расписание покрывает «регулярно»,
порог — «когда приспичило». Две механики доворивают друг друга.

**Риск/митигация.** Ничего не запускается автоматически: только предложение;
выбор целей по-прежнему пустой.

### 5C-2. Расписание: глубокая очистка безопасным набором 🟡

**Что.** В существующую еженедельную тихую задачу добавляем опцию «deep-safe»:
Настройки → расписание → выбор «Smart Clean» / «Deep: безопасный набор».
Deep-safe = цели слоя A, `recommended`, `is_admin` или без блокировки,
+ уже существующая точка восстановления перед стартом (кто включил).

**Почему.** Автоматизация должна использовать план, а не «просто очистить»:
deep-safe использует тот же `Planner` и `clean_plan` с теми же гарантиями
(белый список, возраст, корзина для D), а значит — больше очищает чем Smart,
не увеличивая риск.

**Риск/митигация.** Ти­хий запуск не делает никаких шагов без прав админа;
если стать админом не удалось — записывает в историю `SKIP: нужны права`,
а не падает.

### 5C-3. Auto-discover кэши на экране глубокой очистки 🟢

**Что.** Экран загружает цели реестра + auto-discovered кэши (механизм уже
есть: `discover.auto_discover_items` с 5-минутным кэшем). Отображаем их
в слое A с меткой «авто» и порогом (только содержимое, с подтверждением
как и все).

**Почему.** Констатируем разрыв: Smart видит больше, чем Deep. Достаточно
одного вызова базы: цели уже безопасны (`is_dangerous_target`),
проверяются те же ограничения.

### 5C-4. Остатки программ (D1: orphan-AppData) 🟡

**Что.** Слой D: сравнение установленных программ (данные `uninstaller` уже
читает реестр) с папками первых уровней `%LocalAppData%`/`%AppData%`:
нет установщика с совпадением имени → «остаток» с размером.
Удаление — только в корзину только по отдельному выбору, при этом каждое
срабатывание «осталось безопасно: папка старше 90 дней» + пояснение.

**Почему.** Это единственный слой, где мы реально помогают удалить
накопленное за годы мёртвых приложений (1–5 ГБ типо), сохраняя правило
«пользовательские данные — не без корзины и не без выбора».

**Риск/митигация.** Ложные срабатывания (приложение ставит в реестр не всё):
эвристика требует совпадения *имени*, старше 90 дней, папка не «текущего
активного приложения»; по умолчанию ничего не выбрано.

### 5C-5. Ещё цели (по образцу существующих) 🟢

`NuGet/http-cache`, `Maven`, `Conda pkgs`, `Battle.net cache`, `GOG Galaxy`.
Механика не нова в каждой; добавление пять целей → 0.5–2 ГБ у разработчиков,
и это закрытие списка из FEATURES.md «можно добавить».

## 6. Тесты и Definition of Done

**Новые unit-тесты:**
- `test_dism_target.py` — подмена выхода DISM: `OK`, таймаут, код ошибки;
  `freed` только по дельте.
- `test_hibernation_target.py` — `powercfg` отдаёт код → `SKIP`/`ERR`,
  `restore_hint` в тексте.
- `test_vss_target.py` — парс `vssadmin list shadows`, «оставить последнюю».
- `test_error_kinds.py` — таблица errno→kind и агрегация.
- `test_running_apps.py` — CSV от `tasklist` → предупреждения плана.
- `test_threshold_trigger.py` — порог: срабатывает/не срабатывает.
- `test_schedule_deep_safe.py` — выбор целей слоя A, `SKIP` без прав.
- `test_orphan_appdata.py` — имя совпало/не совпало, порог 90 дней.
- `test_autodiscover_deep.py` — auto-цели на экране и в плане.

**DoD этапа в целом:**
- Ничего не выбрано по умолчанию; необратимое — только отдельное подтверждение.
- Все новые B-действия: «есть права / нет прав / команда упала» дают понятный
  результат, службы не глушатся, `restore_hint` виден в плане.
- Классифицированные ошибки видимы в результате и отчёте.
- Порог и расписание не выполняют вмешательства сами: только предложение,
  подтверждение принадлежит пользователю.
- `ruff`, `mypy`, полный набор тестов зелёные; smoke и скриншоты
  1180×760 и 1024×660 light/dark.

## 7. Риски (чего мы сознательно не делаем)

| Не делаем | Почему |
|---|---|
| `DISM /ResetBase` | необратимо ломает удаление обновлений |
| Ручное удаление `Windows.old` | требует захвата владельца; правильный путь — средства Windows (показ + подсказка) |
| «Очистка реестра» | не даёт места и несёт риск |
| Автоудаление по расписанию слоя C/D | не кэш; права на удаление принадлежат пользователю |
| Автозапуск пороговой очистки без подтверждения | принцип «по умолчанию ничего не выбрано» |

## 8. Порядок работ

1. **5A-2 гибернация → 5A-1 DISM → 5A-3 VSS → 5A-4 показ Windows.old**
   (гигабайты — самое ценное; каждая цель независима, можно остановиться).
2. **5B-1 классификация ошибок → 5B-2 запущенные процессы → 5B-3 метрики → 5B-4 кнопки результата.**
3. **5C-1 порог → 5C-3 auto-discover → 5C-2 расписание → 5C-4 orphan → 5C-5 цели.**
   (5C-4 можно вынести в отдельный релиз v4.8.1, если этап и так большой.)
